# BTN after BB checks: owned solver qualification

The supplied four-BTN-hand connected game now has a separate qualification path for BTN holding **9s Js on 2s 8s Ts**, after BB calls preflop and checks the flop. This is a **made J-high flush**, with check and a half-pot bet as the legal actions. Six seats remain visible in the owned public context; only BTN and BB are active in this continuation.

`SixMaxBtnFlopFeedback` uses a new request/report protocol. It does not change the initial BB or later BB protocols, their saved evidence, the connected game, physical chance, folded blockers or the numerical solver. It is supplied-belief research with no rake, one flop bet and exact checkdown. Qualification of this one decision does not establish general poker GTO or a coherent complete-hand policy.

## Declared reference budget

The request must declare `FRESH_INDEPENDENT_CFR_PLUS_80K_160K/v1`, the ordered iteration counts `[80000, 160000]` and total budget `240000`. Each reference is generated by a **new** CFR+ solver over the complete original connected game. There is no checkpoint continuation, imported policy, automatic escalation or numerical fallback. Original physical payoffs may be cached within the immutable game.

The existing 2,000/4,000-iteration tier cannot qualify this BTN case: those policies have small whole-game best-response gaps but remain outside the original hero security face. New Java negative controls reproduce this distinction. A local quality score cannot replace the face-inclusion check. The new tier is explicit, separately versioned and finite, rather than a change to the old BB tier.

The offline references take approximately eight minutes on the development machine, plus the parent/endpoint solves. A complete replay spends the same declared budget again. This is offline work. Future HTTP integration must load owned evidence before readiness and grade from an immutable cache; it must never solve on a request.

## What must pass

1. Reconstruct the complete original physical game and parent sequence-form solution.
2. Derive the BTN question from owned states and legal edges, including the acting seat and public table history.
3. Select the existing `OWNED_PHYSICAL_FLOP_CONDITIONAL_REACH_EXACT_POWER_TWO_ENDPOINTS/v4` algorithm before optimization and solve both original action endpoints.
4. Require the original-face certified conditional reach above `0.0001`. Keep the original `1e-8` security slack/certificate tolerance and all LP/compiler work limits.
5. Assess the original parent policy and both fresh references against complete-parent and reached-flop quality, actual question reach, counterfactual question reach, original-face inclusion, forced-action optimal future values/loss and selected-decision regret.
6. Require at least one robust within-limit move and one robust outside-limit move at the declared educational limit.
7. On replay, regenerate the complete report and compare every field and policy exactly.

BTN has no own modeled action before this question. **BB's preflop call and BB's flop check both remain in its counterfactual path reach**. The historical BTN raise is part of the supplied input condition; no source policy is available for that prefix. Actual root reach includes the physical flop event, while conditional reach divides by that event's mass. Outside-face references record unchecked bounds, a null bound violation and an explicit rejection.

Only complete owned solve/replay can create `Result` and its private `QualifiedFeedback` capability. Parsed report flags, policy iteration counters and report hashes cannot create that authority. `trainerAdmission` remains false. This milestone supplies qualified offline feedback; a BTN drill/API and a separately versioned collection extension are the next integration work. The existing two-BB-context collection remains unchanged.
